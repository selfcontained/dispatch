## drift_patterns

Observations about where docs tend to go stale. Each run should add new observations and prune ones that no longer apply.

- **User-facing docs drift fastest.** When the app's behavior changes, the in-app docs-pane content is the first thing to notice. It's also the easiest to update in the same PR as the code change (a reviewer can flag stale copy), but in practice it often isn't — so this audit is where it catches up.
- **Settings panes spawn whole new docs sections.** The 2026-04-19 Jobs audit added a `jobs` docs section because the new Jobs settings pane was undocumented in-app. The 2026-04-26 Updates audit did the same for the Updates section in release-manager.tsx, which had a one-paragraph "Assisted update launches a full-access agent..." in the live UI but no docs-pane coverage at all. When a new top-level Settings pane lands, expect to add a corresponding docs-pane section _and_ an entry to `DocsSection` + `SECTIONS`. Cross-check against the `DOCS_SECTION_NAV` list in any README "user-facing docs" sentence — that string drifts every time a section gets added.
- **Form sections evolve from single-checkbox to multi-checkbox.** Watching CRU-139, the "Create git worktree" checkbox grew into a worktree section with a nested "Create a new branch in this worktree" sub-checkbox. This is a recurring pattern: a single-toggle setting accretes a sub-toggle for a previously-implicit behavior. When auditing a "the X checkbox does Y" claim, open the surrounding `<div>` in the dialog component and look for nearby checkboxes — the docs likely describe the original toggle but miss the nested one.
- **Form labels rename without docs updates.** CRU-139 renamed "Create git worktree" → "Create managed git worktree" in the create dialog. The 2026-04-25 audit caught this. When auditing any "click the X button" or "toggle the Y checkbox" claim, grep the literal label string in the relevant component file — labels rename more often than the feature they're attached to, and the docs almost always lag.
- **Review tooling splits across many tools and evolves.** Reviewers used to ping `review_status` with a `status` + `verdict` param; today `review_status` is a pure progress-ping (`message` only) and completion moved to `dispatch_complete_review`. The round-trip loop added five more tools on top, and PR #416 then refactored that loop from poll-based (`dispatch_await_review`/`dispatch_await_recheck`) to push-based (server-injected terminal prompts via `apps/server/src/reviews/injection-prompts.ts`). Every time a review feature lands, expect one of three patterns: a rename/signature-change of an existing tool (often `review_status`), a new tool that splits out a previously implicit step, or — as in PR #416 — a wholesale tooling-shape change where the agent isn't even calling certain tools anymore. Trace from `PERSONA_TOOLS` + parent-side entries in `AGENT_TOOLS` through `apps/server/src/shared/mcp/server.ts` and the review state transitions in `manager.ts` (`reviewing` / `awaiting_recheck` / `complete` / `cancelled`) to keep up.
- **"Sidebar shows X" claims understate what's actually rendered.** 2026-04-22 found the Status Events section said the sidebar shows "the latest event message and a color-coded status indicator" but `agent-card.tsx` actually renders three things: a colored status label, a relative timestamp from `formatRelativeTime`, and the message. When auditing any "sidebar shows" / "card shows" / "page shows" claim, open the actual rendering component (typically in `apps/web/src/components/app/`) and enumerate every span in the JSX — copy tends to mention only the most prominent one. **Corollary added 2026-04-24:** terminal-type agents change which spans render at all (no event indicator, no full-access badge, no feedback panel, no persona launcher). When a new agent type or role lands, recheck every "card shows X" claim against the actual conditional render — `if (isTerminalAgent) return null` patterns scatter through `agent-card.tsx`. **Corollary added 2026-04-26:** sidebar badges have multiplied (Attention / Job / Update). Every new agent role tends to add a badge — `agent-card.tsx:205–235` enumerates them. When auditing the Agents section, grep `<Badge` in agent-card.tsx and make sure every conditional render is mentioned somewhere.
- **Settings defaults flip without the docs noticing.** 2026-04-18 Worktrees run found the docs claimed the default worktree location was `.dispatch/worktrees/` (nested), but `WorktreeLocationSettings` in `apps/web/src/components/app/settings-pane.tsx` actually defaults to `"sibling"`, and so does `manager.ts` (`worktreeLocation = input.worktreeLocation ?? "sibling"`). When auditing a "default" claim in docs, trace it to the component's `useState(...)` initial value AND to the server-side fallback — the two can disagree, and the docs usually follow whichever one was true when the doc was first written.
- **The built-in MCP tool list sprawls without touching the docs.** The 2026-04-18 Repo Tools pass found the docs-pane listed 7 built-in tools; `AGENT_TOOLS` in `apps/server/src/shared/mcp/server.ts` actually has ~19 now (including the round-trip tools). Each new tool gets added to `AGENT_TOOLS` / `JOB_TOOLS` / `PERSONA_TOOLS` but almost never to `docs-pane.tsx`. Grep for `AGENT_TOOLS = new Set` and diff against the `Built-in tools` list in `docs-pane.tsx` whenever touching this area.
- **The create-agent dialog accretes options silently.** When `create-agent-dialog.tsx` gains a field or a visibility gate (e.g. `createType !== "terminal"` hiding Full Access / Autonomous Review / Create-with-prompt for the terminal type), the "Creating an agent" bullet list needs a matching entry. Grep `create-agent-dialog.tsx` for `<Checkbox`, `<label`, and `createType !==` to catch new form fields and visibility gates quickly. The same pattern applies to the add-job and edit-job forms in `jobs-pane.tsx` — they share branch selection via `branch-select.tsx`, so a change there can flow through to both Agent and Job docs sections.
- **Agent types list accretes silently.** `AGENT_TYPES` in `apps/web/src/lib/agent-types.ts` started as `claude/codex/opencode` and now includes `terminal`. Docs-pane and README both reference the list verbatim. Grep for the literal tuple `"claude", "codex", "opencode"` in docs and cross-check against `AGENT_TYPES`.
- **Agents have two orthogonal axes: type and role.** 2026-04-24 added a third dimension: `AgentRole` (`standard` | `assisted_update`) in `manager.ts` and migration 0018, layered on top of `AgentType` (`claude` / `codex` / `opencode` / `terminal`). The two axes are independent — a CLI-type agent can have either role; terminal agents are always `standard` in practice. Docs that talk about "kinds of agents" should be precise: the user-visible Type (CLI-vs-terminal) is set in the Create dialog, while Role is set by special creation paths (assisted-update is created from the release-manager Updates section, not the Create dialog). When documenting a new agent variant, ask: is this a new `type`, a new `role`, or just a behavior gated on an existing flag?
- **Some agents are created outside the Create dialog.** Personas, jobs, and now the assisted-update agent are all spawned through other UI paths — persona-launcher, jobs-pane "Run now", and the release-manager "Assisted update" / gate card. Any "agents are created via..." claim in docs is incomplete unless it covers all four paths.
- **Status indicator colors are theme-driven via CSS vars (`--status-working`, `--status-blocked`, `--status-waiting`, `--status-done`, `--status-idle`).** Don't trust any hard-coded color-name claim in the docs — resolve the actual hue from `apps/web/src/index.css`. 2026-04-18 found the docs had working/done backwards (they'd been copy-pasted from some earlier palette). 2026-04-22 confirmed the current Status Events copy avoids hue claims entirely (says "color-coded"), which is the durable choice.
- **MCP tool sets change by agent type.** The AGENT / JOB / PERSONA tool lists in `apps/server/src/shared/mcp/server.ts` evolve independently. Any doc that enumerates tools for one role is at risk of drifting from the other two. Keep role-specific lists rather than trying to re-list the full set. When documenting a tool, always state which agent types can see it.
- **Some tools are gated dynamically per agent.** `dispatch_await_recheck` was added to the allowed set only when `context.agent?.persona && context.agent.review?.allowRecheck` was true (`mcp/server.ts:493` historically). Docs that imply "persona agents have X tool" may overstate the case for conditionally-allowed tools. When in doubt, grep for `allowed.add(` in `mcp/server.ts`. **Note 2026-04-26:** PR #416's push-based refactor may have removed this gate entirely — verify next run.
- **Repo tool prefix is `repo_`, not `repo.`.** MCP clients don't support dots in tool names, so dots in configured names are sanitized to underscores (`repo-tools.ts`). Docs had `repo.lint` wrong for a long stretch; grep for `repo\.` in docs when reviewing tool-prefix claims.
- **Agent lifecycle has two axes: status and phase.** `status` (`creating`/`running`/…/`archiving`) and `setup_phase` / `archive_phase` are distinct. Docs that mention "phase" without qualifying which one are a drift risk. **Note 2026-04-26:** assisted-update introduced a _third_ set of "phases" (inspect/prepare/apply/restarting/validate/done — see `assisted-update-store.ts`) that are unrelated to the agent setup/archive phases. When documenting "phases" in a future area, name the specific axis.
- **Persona prompt assembly strips legacy placeholders.** `apps/server/src/personas/loader.ts` strips `{{context}}` and `{{diff}}` from persona bodies and appends its own context/diff/feedback-guidance sections. Anywhere the docs describe persona file contents, cross-check against `assemblePersonaPrompt`.
- **Job-related state lives in multiple places.** A "Job" has fields on the DB row (`use_worktree`, `base_branch`, `auto_archive`, `notify`, …), on the `JobRecord` TS type, in the add-job form state (`keepAgent` inverts to `autoArchive`), and in the `buildJobPrompt` preamble that is sent to the agent on every run. When auditing a Jobs claim, trace the field from the UI form → `AddJobConfig` / `JobConfigUpdate` → `JobStore.createJob` / `updateJob` → `JobRecord` → `buildRunConfig` / `buildJobPrompt`. The UI labels (e.g. "Keep agent") do not always match the DB column name (`auto_archive`). **Corollary:** a field can exist on `JobRecord` (e.g. `notify`) without ever being reachable through `AddJobInput` or the form — if you see a feature documented on the record but missing from the input type, assume it's not user-configurable yet.
- **Media formats are gated by two separate allow-lists.** The accepted extensions for `dispatch_share` live in `isMediaFile` / `TEXT_EXTENSIONS` / `DOCUMENT_EXTENSIONS` in `apps/server/src/server.ts`, while the upload-button `accept=` list lives in `ACCEPTED_EXTENSIONS` in `apps/web/src/components/app/media-sidebar.tsx`. They should stay in sync; drift between them creates a confusing UX where an agent can share a format the UI refuses to upload (or vice versa). Diff both when touching either.
- **Notification delivery is multi-channel and they overlap.** Three independent channels (Slack via webhook, web push via SSE `notification` event + ack, sound cues in `use-agent-sound-cues.ts`) all fire off the same `agentManager.onLatestEvent` hook in `apps/server/src/server.ts`. Plus `dispatch_notify` is an agent-initiated fourth path that only hits Slack. Per-channel toggles live in different places — Slack settings + web settings are DB-backed via `slackNotifier`, sound cues are client-side only via `soundCuesEnabledAtom` in `apps/web/src/lib/store.ts`. When documenting "how do I turn X off?", always name which channel.
- **Focus tracker semantics are broader than "terminal open."** `FocusTracker` keys on `agentId` + a 30s TTL, fed by periodic heartbeats from `apps/web/src/hooks/use-agent-focus.ts`. The hook only pulses when `selectedAgentId` is set AND `document.hasFocus()` AND `!document.hidden` — i.e. any tab that has the agent selected, focused, and visible, not specifically the terminal pane. Docs that say "terminal open" or "viewing the terminal" are narrower than reality.
- **Release-flow surface area has metadata-driven UI branches.** The Updates section's Update / Assisted-update / Gate-card branching is driven by `info.assisted` (presence) and `info.assisted.mode` (`normal` / `recommended` / `required`) plus the server-computed `info.assistedRequired` boolean. Docs that describe "the Update button" or "the Assisted update button" need to cover all four states (no metadata, mode=normal, mode=recommended, mode=required), not just the happy path. If a future run revisits this section, walk every JSX branch under `if (info)` in `release-manager.tsx`.
- **CLAUDE.md and AGENTS.md drift from each other.** AGENTS.md got an "Assisted Update Release Notes" section in PR #418 (CRU-143) that CLAUDE.md was missing until the 2026-04-26 audit. The `<!-- Keep behavioral rules in sync with AGENTS.md -->` comment at the top of CLAUDE.md is the canonical pointer; treat any AGENTS.md change as a CLAUDE.md change too. When auditing, run `diff CLAUDE.md AGENTS.md` and look at any block that exists in one but not the other (after accounting for the few legitimately one-sided sections).
