## drift_patterns

Observations about where docs tend to go stale. Each run should add new observations and prune ones that no longer apply.

- **API-spec drift compounds quietly.** The 2026-04-28 audit found `docs/03-api-spec.md` had drifted on six independent surfaces (assisted update, setup/error, two persona-review endpoints, `/jobs/run` body, agent role, agent-types settings) without any single PR being responsible — each landed a route or field, the spec wasn't touched, the gap accumulated. Lesson: when the audit pivots to api-spec, expect to reconcile against `grep -nE '(server|app)\.(get|post|patch|delete)' apps/server/src/server.ts` rather than diff-driven discovery — the diffs since last audit only catch the most recent one or two endpoints.
- **User-facing docs drift fastest.** When the app's behavior changes, the in-app docs-pane content is the first thing to notice. It's also the easiest to update in the same PR as the code change (a reviewer can flag stale copy), but in practice it often isn't — so this audit is where it catches up.
- **Settings panes spawn whole new docs sections.** The 2026-04-19 Jobs audit added a `jobs` docs section because the new Jobs settings pane was undocumented in-app. The 2026-04-26 Updates audit did the same for the Updates section in release-manager.tsx. When a new top-level Settings pane lands, expect to add a corresponding docs-pane section _and_ an entry to `DocsSection` + `SECTIONS`. Cross-check against the `DOCS_SECTION_NAV` list in any README "user-facing docs" sentence — that string drifts every time a section gets added.
- **Form sections evolve from single-checkbox to multi-checkbox.** Watching CRU-139, the "Create git worktree" checkbox grew into a worktree section with a nested "Create a new branch in this worktree" sub-checkbox. This is a recurring pattern: a single-toggle setting accretes a sub-toggle for a previously-implicit behavior. When auditing a "the X checkbox does Y" claim, open the surrounding `<div>` in the dialog component and look for nearby checkboxes — the docs likely describe the original toggle but miss the nested one.
- **Form labels rename without docs updates.** CRU-139 renamed "Create git worktree" → "Create managed git worktree" in the create dialog. When auditing any "click the X button" or "toggle the Y checkbox" claim, grep the literal label string in the relevant component file — labels rename more often than the feature they're attached to, and the docs almost always lag.
- **Review tooling reshapes by deletion as well as addition.** Reviewers used to ping `review_status` with a `status` + `verdict` param; today `review_status` is a pure progress-ping (`message` only) and completion moved to `dispatch_complete_review`. PR #416 refactored the loop from poll-based to push-based and _removed_ `dispatch_await_review` / `dispatch_await_recheck` entirely. Lesson: when a review feature lands, don't just check what's _new_ — also grep for the tool names that were in the docs last time and confirm they still exist.
- **"Sidebar shows X" claims understate what's actually rendered.** When auditing any "sidebar shows" / "card shows" / "page shows" claim, open the actual rendering component and enumerate every span in the JSX — copy tends to mention only the most prominent one. Terminal-type agents change which spans render at all (no event indicator, no full-access badge, no feedback panel, no persona launcher); persona-agent-row has its own state-driven UI surfaces; sidebar badges have multiplied (Attention / Job / Update). Every new agent role tends to add a badge — `agent-card.tsx:205–235` enumerates them.
- **Settings defaults flip without the docs noticing.** When auditing a "default" claim in docs, trace it to the component's `useState(...)` initial value AND to the server-side fallback — the two can disagree, and the docs usually follow whichever one was true when the doc was first written.
- **The built-in MCP tool list sprawls without touching the docs.** Each new tool gets added to `AGENT_TOOLS` / `JOB_TOOLS` / `PERSONA_TOOLS` but almost never to `docs-pane.tsx`. Grep for `AGENT_TOOLS = new Set` and diff against the `Built-in tools` list in `docs-pane.tsx` whenever touching this area.
- **The create-agent dialog accretes options silently.** When `create-agent-dialog.tsx` gains a field or a visibility gate, the "Creating an agent" bullet list needs a matching entry. The same pattern applies to the add-job and edit-job forms in `jobs-pane.tsx`.
- **Agent types list accretes silently.** `AGENT_TYPES` in `apps/web/src/lib/agent-types.ts` started as `claude/codex/opencode` and now includes `terminal`. Docs-pane and README both reference the list verbatim. Server has its own copy at `apps/server/src/agent-type-settings.ts:5` — they must stay in sync.
- **Agents have two orthogonal axes: type and role.** `AgentRole` (`standard` | `assisted_update`) is independent of `AgentType` (`claude` / `codex` / `opencode` / `terminal`). The user-visible Type is set in the Create dialog; Role is set by special creation paths (assisted-update is created from the release-manager Updates section, not the Create dialog). When documenting a new agent variant, ask: is this a new `type`, a new `role`, or just a behavior gated on an existing flag?
- **Some agents are created outside the Create dialog.** Personas, jobs, and the assisted-update agent are all spawned through other UI paths — persona-launcher, jobs-pane "Run now", and the release-manager. The 2026-04-28 audit confirmed there are also two server-side review-launch endpoints (`/agents/:id/launch-review` and `/agents/:id/persona-reviews`) that create persona agents without going through the dialog at all. Any "agents are created via..." claim in docs is incomplete unless it covers all paths.
- **Status indicator colors are theme-driven via CSS vars (`--status-working`, `--status-blocked`, `--status-waiting`, `--status-done`, `--status-idle`).** Don't trust any hard-coded color-name claim in the docs — resolve the actual hue from `apps/web/src/index.css`.
- **MCP tool sets change by agent type.** The AGENT / JOB / PERSONA tool lists in `apps/server/src/shared/mcp/server.ts` evolve independently. Any doc that enumerates tools for one role is at risk of drifting from the other two. Keep role-specific lists rather than trying to re-list the full set. When documenting a tool, always state which agent types can see it.
- **Some tools are gated dynamically per agent.** `dispatch_get_recheck_context` is added to the persona-side allowed set only when `context.agent?.review?.allowRecheck === true`, and `dispatch_cancel_recheck` is gated on the parent side via the same kind of gate. Docs that imply "persona agents have X tool" may overstate the case for conditionally-allowed tools.
- **Repo tool prefix is `repo_`, not `repo.`.** MCP clients don't support dots in tool names, so dots in configured names are sanitized to underscores (`repo-tools.ts`).
- **Agent lifecycle has multiple "phase" axes.** `setup_phase` (worktree/env/deps/session), `archive_phase` (stopping/worktree-check/worktree-cleanup/finalizing), and the assisted-update phase (`inspect`/`prepare`/`apply`/`restarting`/`validate`/`done` + `blocked`/`rollback` from `assisted-update-store.ts`) are three independent state machines. Docs that mention "phase" without naming the axis are a drift risk.
- **Persona prompt assembly strips legacy placeholders.** `apps/server/src/personas/loader.ts` strips `{{context}}` and `{{diff}}` from persona bodies and appends its own context/diff/feedback-guidance sections.
- **Job-related state lives in multiple places.** A "Job" has fields on the DB row, on the `JobRecord` TS type, in the add-job form state (`keepAgent` inverts to `autoArchive`), and in the `buildJobPrompt` preamble that is sent to the agent on every run. The UI labels (e.g. "Keep agent") do not always match the DB column name (`auto_archive`). A field can exist on `JobRecord` (e.g. `notify`) without ever being reachable through `AddJobInput` or the form — if you see a feature documented on the record but missing from the input type, assume it's not user-configurable yet.
- **Media formats are gated by two separate allow-lists.** The accepted extensions for `dispatch_share` live in `isMediaFile` / `TEXT_EXTENSIONS` / `DOCUMENT_EXTENSIONS` in `apps/server/src/server.ts`, while the upload-button `accept=` list lives in `ACCEPTED_EXTENSIONS` in `apps/web/src/components/app/media-sidebar.tsx`. They should stay in sync.
- **Notification delivery is multi-channel and they overlap.** Three independent channels (Slack via webhook, web push via SSE `notification` event + ack, sound cues in `use-agent-sound-cues.ts`) all fire off the same `agentManager.onLatestEvent` hook. Plus `dispatch_notify` is an agent-initiated fourth path that only hits Slack. When documenting "how do I turn X off?", always name which channel.
- **Focus tracker semantics are broader than "terminal open."** `FocusTracker` keys on `agentId` + a 30s TTL, fed by periodic heartbeats from `apps/web/src/hooks/use-agent-focus.ts`. The hook only pulses when `selectedAgentId` is set AND `document.hasFocus()` AND `!document.hidden`. Docs that say "terminal open" or "viewing the terminal" are narrower than reality.
- **Release-flow surface area has metadata-driven UI branches.** The Updates section's Update / Assisted-update / Gate-card branching is driven by `info.assisted` (presence) and `info.assisted.mode` (`normal` / `recommended` / `required`) plus the server-computed `info.assistedRequired` boolean. CRU-146 added a fourth driver — pending update migrations — which can independently force the assisted path even if no `dispatch-update` block exists. Docs that describe "the Update button" need to cover all permutations.
- **CLAUDE.md and AGENTS.md drift from each other.** AGENTS.md got an "Assisted Update Release Notes" section in PR #418 (CRU-143) that CLAUDE.md was missing until the 2026-04-26 audit. The `<!-- Keep behavioral rules in sync with AGENTS.md -->` comment at the top of CLAUDE.md is the canonical pointer; treat any AGENTS.md change as a CLAUDE.md change too.
- **Push-based prompt injection makes some "what the agent sees" claims wrong.** Whenever `apps/server/src/reviews/injection-prompts.ts` (or any future server-side prompt builder) is edited, cross-check the docs that describe what the receiving agent "sees".
