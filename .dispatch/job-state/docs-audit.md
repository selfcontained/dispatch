## drift_patterns

Observations about where docs tend to go stale. Each run should add new observations and prune ones that no longer apply.

- **Operator-facing prose docs accumulate aspirational claims.** The 2026-04-29 ops-runbook audit found three independent claims describing behavior the code never had (auto-rollback, post-update health polling, diagnosis-agent on workflow failure) plus one referenced-but-never-written file (`last-release-failure.log` — only mentioned in the assisted-update prompt template, never opened by the server). Lesson: when auditing operator-facing docs, every "the server does X" claim is suspect. Grep the source for the verb (`spawn`, `writeFile`, `wait`, `poll`, `rollback`) and confirm the call exists. Don't assume docs that match a plausible mental model match the code.
- **API-spec drift compounds quietly.** The 2026-04-28 audit found `docs/03-api-spec.md` had drifted on six independent surfaces without any single PR being responsible — each landed a route or field, the spec wasn't touched, the gap accumulated. When the audit pivots to api-spec, expect to reconcile against `grep -nE '(server|app)\.(get|post|patch|delete)' apps/server/src/server.ts` rather than diff-driven discovery — the diffs since last audit only catch the most recent one or two endpoints. New 2026-05-04 confirmation: PR #493 added three more auto-check endpoints and an SSE event without an api-spec touch.
- **Lifecycle/runbook doc drift is the same shape as API-spec drift.** Dev/ops-facing prose docs grow many small independent gaps without any single PR breaking them. Expect them to need full re-grounding against the source of truth (`apps/server/src/agents/manager.ts`, `assisted-update-store.ts`, `apps/server/src/server/release-runtime.ts`) rather than diff-driven patching when they get touched.
- **User-facing docs drift fastest.** When the app's behavior changes, the in-app docs-pane content is the first thing to notice. It's also the easiest to update in the same PR as the code change (a reviewer can flag stale copy), but in practice it often isn't — so this audit is where it catches up.
- **Settings panes spawn whole new docs sections.** The 2026-04-19 Jobs audit added a `jobs` docs section because the new Jobs settings pane was undocumented. The 2026-04-26 Updates audit did the same for the Updates section. The 2026-05-02 Personalities audit did the same. The 2026-05-03 Agents audit added Tmux scrollback as a subsection. The 2026-05-04 run added a full "Keyboard Shortcuts" section. Pattern refinement: a keyboard / command-palette layer is a docs section because the feature surface (5 hotkeys + 5 palette actions) is large enough and self-contained enough to warrant its own nav entry.
- **New keyboard layers land without docs.** PR #483 added five global hotkeys + a Cmd+K command palette and PR #488 wired hotkeys to fire from inside text inputs and the terminal. Now documented as of 2026-05-04. Retain this observation for future hotkey additions: watch for `useHotkey` / `data-hotkey-disable` / cmdk imports in future diffs.
- **Form sections evolve from single-checkbox to multi-checkbox.** Watching CRU-139, the "Create git worktree" checkbox grew into a worktree section with a nested "Create a new branch in this worktree" sub-checkbox. Recurring pattern: a single-toggle setting accretes a sub-toggle for a previously-implicit behavior. When auditing a "the X checkbox does Y" claim, open the surrounding `<div>` in the dialog component and look for nearby checkboxes — the docs likely describe the original toggle but miss the nested one.
- **Form labels rename without docs updates.** CRU-139 renamed "Create git worktree" → "Create managed git worktree". When auditing any "click the X button" or "toggle the Y checkbox" claim, grep the literal label string in the relevant component file — labels rename more often than the feature they're attached to, and the docs almost always lag.
- **Review tooling reshapes by deletion as well as addition.** Reviewers used to ping `review_status` with a `status` + `verdict` param; today `review_status` is a pure progress-ping (`message` only) and completion moved to `dispatch_complete_review`. PR #416 refactored the loop from poll-based to push-based and removed `dispatch_await_review` / `dispatch_await_recheck` entirely. When a review feature lands, don't just check what's new — also grep for the tool names that were in the docs last time and confirm they still exist.
- **"Sidebar shows X" claims understate what's actually rendered.** When auditing any "sidebar shows" / "card shows" / "page shows" claim, open the actual rendering component and enumerate every span in the JSX — copy tends to mention only the most prominent one.
- **Settings defaults flip without the docs noticing.** When auditing a "default" claim in docs, trace it to the component's `useState(...)` initial value AND to the server-side fallback — the two can disagree, and the docs usually follow whichever one was true when the doc was first written.
- **The built-in MCP tool list sprawls without touching the docs.** Each new tool gets added to `AGENT_TOOLS` / `JOB_TOOLS` / `PERSONA_TOOLS` but almost never to `docs-pane.tsx`. Grep for `AGENT_TOOLS = new Set` and diff against the `Built-in tools` list in `docs-pane.tsx` whenever touching this area.
- **The create-agent dialog accretes options silently.** When `create-agent-dialog.tsx` gains a field or a visibility gate, the "Creating an agent" bullet list needs a matching entry.
- **Agent types list accretes silently.** `AGENT_TYPES` in `apps/web/src/lib/agent-types.ts` started as `claude/codex/opencode` and now includes `terminal`. Docs-pane and README both reference the list verbatim. Server has its own copy at `apps/server/src/agent-type-settings.ts:5`.
- **Agents have two orthogonal axes: type and role.** `AgentRole` (`standard` | `assisted_update`) is independent of `AgentType` (`claude` / `codex` / `opencode` / `terminal`).
- **Some agents are created outside the Create dialog.** Personas, jobs, and the assisted-update agent are all spawned through other UI paths.
- **Status indicator colors are theme-driven via CSS vars (`--status-working`, `--status-blocked`, `--status-waiting`, `--status-done`, `--status-idle`).** Don't trust any hard-coded color-name claim in the docs.
- **MCP tool sets change by agent type.** The AGENT / JOB / PERSONA tool lists in `apps/server/src/shared/mcp/server.ts` evolve independently.
- **System-prompt injection has a per-flow allowlist.** Personalities are appended only for "regular" launches — explicitly NOT for `input.persona`, `input.jobRunId`, or `role === "assisted_update"`.
- **Repo tool prefix is `repo_`, not `repo.`.** MCP clients don't support dots in tool names, so dots in configured names are sanitized to underscores.
- **Push-based prompt injection makes some "what the agent sees" claims wrong.** Whenever `apps/server/src/reviews/injection-prompts.ts` or any server-side prompt builder is edited, cross-check the docs.
- **Auto-rename prompter is a push injection.** New 2026-05-04 observation: `auto-rename-prompter.ts` injects a canned `RENAME_PROMPT` on the first terminal→working transition for agents with default names. It's now documented in docs-pane Agents → "Renaming agents", but the sidebar Tag button's visibility condition (`running + hasDefaultSessionName`) depends on three negative checks (persona, terminal, job-prefix) — any new "invisible" agent flavor needs the same exclusion or the button leaks.
- **Automatic update check introduced a new SSE event.** PR #493 added `release-info` as an SSE event type (broadcast whenever the server-side cached snapshot changes). The Updates docs-pane section now mentions auto-check, but the SSE schema itself is undocumented (clients receive a full `ReleaseInfoSnapshot`). If a future run audits the streaming / SSE surface, include this event.
- **Per-install state files live outside the repo checkout.** `~/.dispatch/release.json` (deployed tag), `~/.dispatch/assisted-update.json` (in-flight assisted state), `~/.dispatch/applied-migrations.json` (CRU-146), `~/.dispatch/cache/release-<tag>.tar.gz` (artifact cache).
- **CLAUDE.md and AGENTS.md drift from each other.** AGENTS.md got an "Assisted Update Release Notes" section in PR #418 (CRU-143) that CLAUDE.md was missing until the 2026-04-26 audit.
- **Media formats are gated by two separate allow-lists.** The accepted extensions for `dispatch_share` live in `isMediaFile` / `TEXT_EXTENSIONS` / `DOCUMENT_EXTENSIONS` in `apps/server/src/server.ts`, while the upload-button `accept=` list lives in `ACCEPTED_EXTENSIONS` in `apps/web/src/components/app/media-sidebar.tsx`.
- **Notification delivery is multi-channel and they overlap.** Three independent channels (Slack via webhook, web push via SSE, sound cues) all fire off the same `agentManager.onLatestEvent` hook. Plus `dispatch_notify` is an agent-initiated fourth path.
- **Focus tracker semantics are broader than "terminal open."** `FocusTracker` keys on `agentId` + a 30s TTL, fed by periodic heartbeats from `use-agent-focus.ts`.
