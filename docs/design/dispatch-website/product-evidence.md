## Install/platform facts

- **Native Mac: macOS 13+, Apple Silicon.** Stable `apps/macos/Package.swift:13` sets macOS 13; actual release asset is arm64 only. `docs/macos-app.md` describes menu bar app, private bundled PostgreSQL 17, default-browser UI, Sparkle updates, and separate agent CLI/auth prerequisites. `docs/macos-releases.md` explicitly says Intel native delivery is not implemented. No Windows release was evidenced.
- **Mac defaults differ from Linux:** native data is `~/.dispatch-mac/`, default web port **6768**, app-owned HTTPS with a locally generated CA. Device trust is explicit; network addresses are chosen in native Settings. See `docs/macos-app.md` Data and Local HTTPS sections. Do not reuse standalone `~/.local/share/dispatch` / 6767 guidance for the native app.
- **Linux:** Stable `bin/install-dispatch.sh` requires PostgreSQL **14+**, creates private DB/credentials via available Postgres administration (normally `sudo`), stores config under `~/.local/share/dispatch/server/.env`, registers `dispatch-server` systemd user service, and defaults to **127.0.0.1:6767** or next free port. `--host 0.0.0.0` enables LAN/Tailscale-facing binding. The host needs systemd/service support for that documented service path; `--no-service` is a separate mode.
- **Architecture scope:** Stable `scripts/build-bun-binaries.mjs:29–32` targets Darwin/Linux x64 and arm64; installer detects these pairs. This supports standalone binary build intent; tarball contents were not extracted in this audit. Distinguish a Darwin x64 standalone target from an available Intel native Mac app.
- Released compiled server needs no Node/pnpm/Bun merely to run Dispatch. **Agent CLIs and project commands retain their own runtime requirements.** Source development prerequisites are a separate path. Do not copy README’s Codex package/auth commands verbatim without a separate current CLI-doc check.
- Installer defaults to promoted Stable (Preview fallback only when no Stable exists). Native Stable is default; Preview is opt-in under Settings → Support → Updates. 1.x is a fresh-install/new-DB line, not an in-place migration from unsupported 0.x (`README.md`, installer, site docs).

## Local-first and trust boundaries

- Safe: “Dispatch runs on your Mac or Linux machine, using your repositories and agent CLIs, with local PostgreSQL and files.” **Do not say** offline AI, no data ever leaves the machine, air-gapped by default, or all models run locally. Provider CLIs, GitHub releases, optional Slack/browser connections and project tools can use external services. OpenCode can use configured local models, but that does not make every installation offline.
- Stable access implementation: `apps/server/src/agents/acp/engine-spec.ts`, `permissions.ts`; `docs/design/acp-runtime.md` Access and permission requests. Full-access mode bypasses/allows engine approvals; restricted modes vary by engine. Claude checks and OpenCode build/plan modes are not OS sandboxes. Worktrees do not restrict filesystem access. Login-shell credentials and local config are consequential trust boundaries.
- `apps/server/src/auth.ts` and `apps/server/src/routes/auth.ts` implement an installation password and device-session cookies. No verified individual-user accounts, tenant isolation, team RBAC, enterprise SSO, audit-compliance certification, or hosted collaboration service. “Team workspace” should not imply those features.
- Browser access from another device is supported only after arranging reachability, binding and (for native HTTPS) device certificate trust. Local-first does not mean automatic public hosting or remote machine orchestration.
- **Aspirational:** `docs/linked-instances-plan.md` explicitly says “design agreed, not started. No implementation exists on main.” Do not advertise linked installations, cross-machine agent launching/federation, cloud worker pools or seamless laptop-to-cloud execution as shipped.

## Existing-site copy corrections / caveats

1. `apps/site/src/pages/docs.astro:10` and README retain “before first Stable promotion” guidance. Stable v1.4.4 now exists. Historical conditional is technically conditional but distracts and makes current installation guidance look pre-launch.
2. “Newest release” for Mac may take users to Preview v1.5.4 while app follows Stable. Offer an explicit Stable destination and a separately labeled Preview route; do not equate chronology and channel.
3. Docs imply one install directory/port for Dispatch generally; native Mac actually uses `~/.dispatch-mac/` and 6768 with managed HTTPS. Separate platform setup.
4. `docs.astro` names only Claude/Codex as recommended. This is compatible with “recommended,” but incomplete as a support inventory: OpenCode is already present in Stable. “Most often exercised” is not quantified by evidence here.
5. `index.astro` “agent is still running” at a later handoff needs the machine/process/provider availability condition. Avoid absolute “never loses work” language.
6. “Humans and agents can change the same repository without ... disturbing each other” overstates worktree guarantees: directories/branches are separate, shared resources and eventual merges still need coordination.
7. Site “shared workspace/team” language is experiential positioning, not evidence of separate user identities or access controls. Ground it in browser access, streams, shared files, and local execution.
8. Current site omits task boards/triggers. They are legitimate **Preview** capabilities; do not silently promote them to Stable in a redesign.

No performance, cost-saving, concurrency-limit, security-certification, customer adoption or productivity statistics were verified. Avoid adding them. This audit establishes implementation/publication evidence, not fresh live behavioral verification or inspection of deployed website bytes.
