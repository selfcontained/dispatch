# Linked Instances — Design Plan

**Status:** design agreed, not started. No implementation exists on `main`.

This captures where a design discussion landed so the work can be picked up later
without re-deriving it. It supersedes the approach in
[PR #978](https://github.com/selfcontained/dispatch/pull/978), which is not being
merged but is worth reading as a reference implementation — several pieces of it
should be lifted more or less intact.

---

## 1. What this feature is

Let one Dispatch install coordinate agents running on other machines: a laptop
driving a cloud box, a desktop, or a CI host. Two motivations, and they want
different things:

- **Humans** want to see and control work running elsewhere.
- **Agents** want to launch and message collaborators regardless of which machine
  they are on.

Most of the difficulty in #978 came from trying to serve both with one mechanism.
Separating them is most of the fix.

## 2. Where PR #978 went wrong

#978 works. It is 45 files, +5,684/−74, and it is not merging for two structural
reasons.

**It built a federation API where it needed a transport.** Four hand-written
cross-instance endpoints — `/peers/launch`, `/peers/messages`, `/peers/events`,
`/peers/repos` — each with its own schema, capability gate, client, and error
mapping. Terminal would have been a fifth, media a sixth. Every feature that
crosses instances pays the tax again, so branch count scales with feature count.
It already shows: five behavioral `if (peerId)` branch sites server-side, six
web-side.

**It coupled authorization to Tailscale.** `tailscale whois` on the caller's
socket, matched against a StableID pinned at pair time, is what makes a stolen
bearer token useless from another machine. That is not a networking detail that
can be swapped out — it is the identity proof, and removing Tailscale means
replacing it.

## 3. The architecture we landed on

### 3.1 Hub and spoke, between ordinary installs

One install coordinates others. The relationship is asymmetric — a spoke is
_claimed_ by a hub — but **both ends are the same product**: one binary, one
release, one version number. The role is per-link, so a laptop can be hub to a
cloud box and spoke to a desktop.

`DISPATCH_MODE=spoke` exists only as a deployment convenience (skip serving the
UI, skip the scheduler). It is not a separate artifact. See
§7 for why a genuinely headless "engine" was considered and rejected.

### 3.2 Trust: pinned mTLS on a dedicated port

At pair time each side generates a keypair and self-signed certificate, and the
handshake exchanges **fingerprints** alongside bearer tokens. Every connection
thereafter is mTLS verifying the pinned fingerprint. The trust anchor is the
peer's own certificate, not a public CA:

```js
// spoke's peer listener
https.createServer({
  key: peerKey,
  cert: peerCert,
  ca: pinnedPeerCerts, // literally: the certs of hosts we paired with
  requestCert: true,
  rejectUnauthorized: true,
});
```

Dialing out mirrors it — `ca: [thatHostsCert]` plus a `checkServerIdentity` that
compares `fingerprint256` instead of matching a hostname.

Consequences worth knowing:

- **No HTTPS requirement for the human API.** `TLS_CERT`/`TLS_KEY` stays the
  optional thing it is today. The peer port is separate and no browser touches it.
- **Hostname is irrelevant.** Overriding `checkServerIdentity` is what lets you
  dial a raw IP, a `.local` name, or a tailnet name with one certificate. This is
  what makes "whatever network you're on" work.
- **A dedicated peer port removes a bug class.** The port speaks only mTLS, so
  there is no "is this caller authenticated" question on it. #978's entire
  first-run hardening — the `isLoopback` arrival-interface gate, the
  `wildcard-host` case, the password interlock — becomes unnecessary by
  construction.
- **Keep the peer certificate separate from `config.tls`.** A Let's Encrypt cert
  is a hostname assertion and rotates every 90 days; the peer cert is an identity
  and should live for years. Conflating them means every renewal breaks
  federation.

Certificate generation needs a library — `node:crypto` makes keypairs but not
X.509. `selfsigned` is the smallest option. Generate once at first boot, persist,
never touch again. **Regenerating invalidates every pin**, so make that error say
"re-register this host" rather than surfacing a raw TLS failure.

### 3.3 Registration, not pairing

#978's handshake is symmetric — six-digit code, TTL, bidirectional credential
issue — because it assumed two equals. Hub↔spoke is asymmetric, so registration
can be a single token generated by the hub and supplied to the spoke at install:

```
dispatch register --hub https://laptop.local:6767 --token <token>
```

No code, no TTL, no pairing UI, no reverse credential. Trust on first use, pinned
thereafter; show the fingerprint on both ends for confirmation, the way SSH host
keys and Signal safety numbers work. For the real threat model — machines the
same person owns — that is proportionate. Don't build more.

### 3.4 Routing: one dumb proxy

The browser only ever talks to its **local** install. Never a remote one:

- The remote's certificate is self-signed and pinned by the server, not a CA — a
  browser hitting it gets an interstitial.
- The remote may not be routable from the browser's network even when it is from
  the server's.
- Cookies, CORS, and auth are scoped to one origin.

So the hub proxies, under a path prefix:

```
client → hub    /api/v1/host/inst_b/agents/agt_xyz/pins
hub    → spoke  /api/v1/agents/agt_xyz/pins
```

Strip the prefix, forward the rest verbatim, stream the response back. **The proxy
never parses the path.** That is the point: it works for endpoints it has never
heard of, including a spoke running a newer Dispatch.

The alternative — resolve the agent id server-side and route transparently —
forces a routing table for every id-bearing resource type and rewriting of URLs
embedded in response bodies, and only works for paths the proxy knows the shape
of. Rejected.

| Request class          | Handling                                                                                                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REST                   | Prefix and forward. Pins, reviews, media metadata, lifecycle, diffs.                                                                                                                   |
| WebSocket              | Proxy the upgrade, pipe both directions. The terminal token is minted by the spoke and fetched through the same proxy, so nothing forges auth. **Terminal parity falls out for free.** |
| Global SSE             | Not proxied. See §3.6.                                                                                                                                                                 |
| Media transfer         | Prefix and forward, but **stream** — don't buffer. Otherwise a 100 MB recording is a memory spike.                                                                                     |
| Static, settings, jobs | Always local.                                                                                                                                                                          |

Pair-time capabilities become a route-pattern → capability table checked once at
the proxy, rather than a gate inside each handler.

### 3.5 Client: a host selector, not a merged list

A top-level host selector scopes the whole UI. You are looking at one machine at a
time; listing and creating agents respect the active host. The active host belongs
in the URL (`/h/inst_b/...`) so it is deep-linkable and survives reload.

This is the decision that collapses the most complexity:

- No merged agent list, no shadow rows, no presence cache, no reaping or
  unreachable-stamping, no drift between multiple SQL writers. **Most of #978's
  weight is avoided rather than solved.**
- Instance-scoped and repo-scoped resources (jobs, templates, settings, media,
  brain, personas) just follow the selector. The scoping problem stops being a
  design question.
- Agent id collisions stop mattering early on.
- The mental model — "switch which machine I'm looking at" — needs no explanation.

What you give up: no everything-at-once view, and attention doesn't cross hosts.
The incremental fix for the second is a count badge on the selector, which does
**not** require merging the lists.

### 3.6 Version compatibility

Because the browser only ever talks to its local install, the problem splits into
two halves and each is tractable:

- **UI ↔ its own backend** is always in lockstep. Same install, same version. The
  existing `X-Dispatch-Version` reload banner keeps working as designed.
- **hub ↔ spoke** is server-to-server, and **the hub is a place where you can
  adapt.** Missing field? Default it. Renamed status? Map it. Endpoint absent?
  Return a clean "not supported by that host" instead of a broken button.

You cannot write compatibility shims in a browser bundle you do not control. You
can write them in your own server. That difference is why this model wins, and
why serving the remote's UI bundle and Module Federation were both rejected (§7).

**Immediate landmine:** `apps/web/src/lib/version.ts` compares every response's
`X-Dispatch-Version` against the bundle's compiled-in version and flips a
permanent reload banner on mismatch. Proxied responses carry the _spoke's_
version, so the banner fires the moment you switch hosts and reloading never
clears it. **The mismatch check must only consider responses from the local
host.** The remote's version belongs in the host selector as information, not as a
reload prompt.

Policy: a `peerApiVersion` integer that bumps only on breaking contract changes,
decoupled from the release version. Support a narrow window (N and N−1) and refuse
outside it with a clear message — which is affordable precisely because of §3.7.

### 3.7 Hub-managed updates

The hub knows each spoke's version and already tracks releases for itself. It
offers "update Cloud to 0.41" in the hosts list. This is what keeps the
compatibility window narrow enough to avoid a permanent shim tax.

Three things to get right:

- **Send a version, not bytes.** The spoke fetches and verifies the release
  artifact itself from the official source. Letting the hub push a binary makes
  the link a remote-code-execution channel and a compromised hub owns every
  spoke.
- **"Updating" is a distinct state from "unreachable."** The spoke restarts, so
  the link drops as a normal part of the flow. Without this state a successful
  update reads as a dead host every time.
- **Auto-revert on failed health check.** A headless cloud box that comes back
  unhealthy may have no other way in. Keep the previous binary, health-check the
  new one, roll back automatically. The existing candidate/promote-on-healthy
  pattern is the right precedent; the revert half needs to be automatic.

Ordering: hub updates first (user-driven), then surfaces "2 hosts need updating."
The N−1 window covers the gap.

## 4. Long-term vision for agent collaboration

**Humans navigate; agents address.** The host selector is a human affordance — an
agent cannot "switch hosts," it must _name_ a collaborator that might be anywhere.

The end state is **one fleet, many machines**: where an agent runs is a property of
it, like `cwd` or `type`, not a namespace boundary.

- **Global ids, no qualified addressing.** `agt_` ids are `randomUUID()` truncated
  to 12 hex — 48 bits, effectively globally unique. A spoke's ids can be stored
  verbatim, so `dispatch_send_message` takes a bare id and the host is a lookup,
  not part of the name. #978's `inst_x:agt_y` scheme disappears, and with it the
  regex that broke on agent names containing colons.
- **Host is a placement constraint, not a different API.** `dispatch_launch_agent`
  gains a host parameter the way it has `fullAccess` — one pipeline, one tool. The
  interesting long-term version is capability-based ("needs a GPU", "has the prod
  credentials") rather than name-based.
- **Lineage becomes a soft pointer.** Today `parent_agent_id` is an FK, which is
  _the_ reason #978 needs shadow rows — you cannot reference a row on another
  machine. Make lineage `{id, host}` resolved lazily and cross-host delegation
  trees work with no shadow rows at all.
- **Link failure must reach agents, not just the UI.** #978 surfaces
  unreachability to the sidebar only. An agent awaiting a reply from a machine
  that closed its lid waits forever. Dead-letters and timeouts need to come back
  as observable outcomes. **This is the failure mode most likely to break the
  feature in practice.**
- **Context does not travel implicitly.** #978's remote-launch preamble is honest
  about this — you start fresh, the prompt is the whole briefing, ask if you need
  more. Keep that.

Note the inversion: **unification is an agent requirement, not a human one.** The
host selector removes the need for a merged list in the UI, but agents genuinely
need to see across hosts. That is what justifies a presence cache later, not the
sidebar.

## 5. Phased releases

Sequential releases, each merged and shipped before the next starts — not a PR
stack. The feature is self-gating (nothing changes until a host is registered), so
pieces can land on `main` independently and `main` stays releasable throughout.

| #   | Release                       | Ships                                                                                                                                    | Value                                                                                       |
| --- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| R1  | Connect two hosts             | Instance identity, cert generation, mTLS peer port, registration flow, capability table, hosts settings panel with health and unregister | Machines are linked; you can see the link is healthy                                        |
| R2  | Host selector                 | Prefix proxy (REST, WS upgrade, streaming, capability enforcement) + the selector and its URL state                                      | **All of Dispatch pointed at another machine** — list, terminal, launch, media, diffs, pins |
| R3  | Attention badge               | Per-host blocked/unread counts on the selector                                                                                           | Flipping hosts is informed rather than a guess                                              |
| R4  | Agent-initiated remote launch | `host` parameter on the MCP launch tool, provenance recorded on both ends                                                                | Agents delegate across machines (humans already can, via R2)                                |
| R5  | Cross-host agent messaging    | Outbox, idempotency receipts, dead-lettering, two-sided message record                                                                   | Agents coordinate across machines                                                           |

R1 and R2 could reasonably ship together — the selector makes R2 small.

Independent of all of it: **the first-run loopback fix from #978** is a real
security fix on its own merits and should ship as its own PR.

Within R1 the merge order is roughly: identity + certs → peer port + mTLS →
registration routes + capability table + migration → settings panel.

**Migrations stay additive, one per release, never renumbered.** Check the
production `pgmigrations` table before picking numbers — #978 already had to
renumber `0041 → 0042` when upstream took the slot.

R1 introduces a new listening port, which is what
`release-notes/next-assisted-update.json` exists for. Author metadata so upgrades
don't quietly fail behind a firewall or service-manager config.

| Component                                                                                                               | Verdict                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Capability columns (launch / message / full-access / events) and the reasoning behind them                              | **Keep.** Becomes the proxy's route-pattern policy table. Add `allow_terminal`.            |
| `PeerEventSubscriber` — fingerprint-on-reconnect, snapshot-supersedes, backoff                                          | **Keep** for R3/R5. A subscription is not a proxy problem.                                 |
| Outbox, backoff, dead-lettering, idempotency receipts                                                                   | **Keep** for R5. The content-vs-state durability split is the sharpest idea in the PR.     |

| Launch fork (`handleLaunchAgentOnPeer`), the four hand-rolled shadow-write SQL sites, every `if (peerId)` in a handler  | **Drop.**                                                                                  |

## 7. Rejected alternatives

- **Tailscale as the trust mechanism.** Requires an external daemon and a CLI on
  PATH, costs a subprocess with a 10s timeout per authenticated request, parses
  semi-stable CLI JSON, and only works on a tailnet. Pinned mTLS is stronger and
  works anywhere packets route. Users who want Tailscale still get it — that's
  their network doing its job, not a Dispatch feature.
- **A separate headless "engine" artifact.** Investigated in depth. The audit
  found the dependency win is near zero (`apps/server` has twelve runtime
  dependencies and no frontend packages; the saving is a web bundle) and that
  every other claimed benefit — version compatibility, hub-managed updates,
  simpler registration — comes from the **topology**, not from the spoke being
  headless. A second artifact costs a second release path, a second install path,
  a second assisted-update story, and a standing "which side owns this" question.
  Rejected in favour of `DISPATCH_MODE=spoke` as a flag.
- **Serving the remote's UI bundle through the proxy**, and **Module Federation.**
  Both aim at eliminating version skew by pairing each frontend with its own
  backend. Unnecessary once the browser only talks to its local install, since the
  hub can then normalize. Module Federation is additionally a poor fit: its
  defining feature is _shared_ singleton dependencies, and the goal here is
  _isolation_.
- **A dedicated activity/timeline pane for remote agents.** #978 needs one because
  it cannot relay a terminal. The proxy can, so the constraint that justified the
  pane is gone. `agent-history-timeline.tsx` already exists and is not heavily
  used.
- **Re-keying the brain on a canonical repo identity.** Proposed to enable
  cross-host brain sharing, then dropped: working directories are not always
  repos (`listLocalRepos` already does `COALESCE(git_context->>'repoRoot', cwd)`),
  repos don't always have remotes, and cross-host brain sharing was never an
  agreed goal. Revisit only if §8 resolves toward sharing.

## 8. Open questions

- **Does the brain federate?** Now has a real motivation (two agents collaborating
  on one project across two machines) rather than a hypothetical one. Hub-owned
  with spokes reading through is the most likely answer and is a better shape than
  anything the peer-to-peer model offered.
- **How does an agent learn its message didn't arrive?** §4. Needs a deliberate
  design, not whatever the transport happens to do.
- **Where do reviews live?** The one subsystem that doesn't sort cleanly.
  `agents/reviews.ts` touches `reviews`, `review_feedback_items`, and
  `review_thread_messages` heavily — agent-scoped in the schema, hub-shaped in use
  (written by agents, read and resolved by people).
- **Terminal access to a spoke while the hub is down.** The UI only exists at the
  hub, so an agent stuck at 2am on a spoke is unreachable. A minimal direct-attach
  path on the spoke would be cheap now and expensive to retrofit.

## 9. Two defects in #978 worth fixing regardless

**Cross-instance messages are never recorded.** In
`apps/server/src/server/mcp-handlers.ts`, the qualified-address branch of
`handleSendMessage` returns at line 920; `insertMessage` is at line 1039. A
cross-instance message is delivered as a prompt injection and never written to
`agent_messages` on either side — no entry in the messages panel, no contribution
to `unreadMessageCount`, no thread history. Locally-sent messages do all three.

**The launching host cannot intervene.** On the launching instance a remote agent
is read-only for humans. The terminal is inert by design, but `inject-text`,
`inject-phrase`, and `inject-pin` all call `getTerminalAccess` and return 409, so
quick phrases, pin shortcuts, and the mobile keyboard break too; the messages UI
is read-only with no compose box. The only channel into a remote agent is another
_agent_ calling `dispatch_send_message`. Nobody chose this — those routes branch on
the mechanism (is there a tmux session?) instead of the capability (can I deliver
text to this agent?). Moot under the proxy design.
